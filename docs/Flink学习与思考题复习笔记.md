## 三、第一讲：流处理与 Flink 全景

### 1. 本讲主题和学习目标

主题：建立实时数仓的整体认知，回答三个面试必问题。
目标：① 能答"为什么选 Flink"；② 讲清 Flink 架构三角色；③ 知道本项目每一层用哪套 API。

### 2. 核心概念及通俗解释

- **有界数据 / 无界数据**：有界 = 一批一批、跑完就停（如昨天的订单）；无界 = 持续到达、永不结束（如用户点击流）。
- **批处理 / 流处理**：批处理攒够一批算一批，T+1 出结果；流处理来一条算一条，毫秒到分钟出结果。
- **微批**：把流按时间切成小段，每一段当一个小批处理。本质是"批假装流"。
- **真流**：事件逐条处理，管道里始终有数据流动。
- **实时数仓**：用流处理引擎做数仓分层（ODS→DWD→DWS→ADS），把分析延迟从天级降到分钟/秒级。
- **事件驱动**：系统由到来的每个事件触发处理，而不是定时轮询。
- **exactly-once**：每条数据恰好被处理一次，不丢不重。
- **JobManager（JM）**：作业总控，相当于指挥官。
- **TaskManager（TM）**：真正执行算子的进程，相当于干活的人。
- **Slot**：TM 内部的资源单位（内存+线程的抽象），不是 CPU 核。
- **并行度**：用多少个 Slot 同时干活。
- **算子链**：上下游算子无需网络传输时合并成一个 task 一起跑，省序列化和网络开销。
- **三层 API**：Flink SQL/Table API（写 SQL）→ DataStream API（编程式）→ ProcessFunction（最底层，直接控状态和定时器）。

### 3. 重要原理与执行过程

**三代引擎演进（面试必背）**：

| 引擎 | 本质 | 问题 |
|---|---|---|
| Storm (2011) | 真流 | 吞吐低、无状态管理、at-most-once，已过时 |
| Spark Streaming (2013) | 微批 | 秒级延迟，"批假装流" |
| Flink (2016~) | 逐条事件驱动 | 毫秒级延迟、状态+checkpoint→exactly-once、事件时间生态成熟、国内实时数仓事实标准 |

**Flink 四大优势**：① 真流毫秒延迟 ② 状态管理+checkpoint→exactly-once ③ 事件时间/watermark 生态最成熟 ④ 阿里 Blink 回馈，国内大厂标准。

**作业提交流程（按顺序背）**：Client 提交作业 → JobManager 解析作业生成 JobGraph → 切分执行图 → 分配任务到各 TM 的 slot → 运行；JobManager 全程协调 checkpoint，故障时恢复。

**算子链断开条件**：keyBy 重分区、并行度不同、共享组不同时，算子链会断开。

**API 选型原则**：能用 SQL 用 SQL，SQL 表达不了的用 DataStream，再底层用 ProcessFunction。开发效率从上往下递减，控制力从下往上递增。

### 4. 典型例子及分析过程

- **自己两个项目的对照**：医疗项目 = 批处理（数据先落库再分析，T+1 可接受）；招聘广告 = 流处理（广告主看分钟级效果实时调价，等一天没意义）。
- **模板项目（Spark 版）的两个关键代码**：
  - `jobs/kafka_to_cassandra_mysql_stream.py:158`：`.trigger(processingTime="30 seconds")` → 30 秒一个微批，延迟被批间隔锁死。
  - 同文件 `:53`：`.dropDuplicates(["id"])` → 无状态去重，只在当前批内去重。
- **本项目 Flink 版链路**：CSV 回放 → Kafka（ODS）→ Flink SQL DWD（解析+过滤+维表 join）→ DWS（分钟级窗口聚合）→ ADS（小时累计）→ MySQL → Grafana。

**本项目 4 个改造亮点（简历卖点，每个都要能指代码讲）**：
1. 原版 30s 微批+批内去重 → Flink 事件时间+watermark+状态去重
2. 原版无维表关联 → 用 search.csv 维表 join 补 publisher/campaign 维度
3. 原版无乱序处理 → 迟到数据侧输出流重算
4. 原版 TRUNCATE stage+INSERT 非事务 → 幂等 upsert 写入

### 5. 易混概念对比

| 对比项 | A | B | 关键区别 |
|---|---|---|---|
| 批处理 vs 流处理 | 有界数据、一次性产出 | 无界数据、持续更新 | 数据是否有界、结果何时产出 |
| 微批 vs 真流 | 攒段→切批→跑批 | 逐条处理 | 延迟 ≈ 批间隔 vs 逐条；班车 vs 出租车 |
| Spark vs Flink | 批装流 | 真流 | 状态更新粒度（批 vs 条）、乱序处理、恢复机制 |
| Slot vs CPU 核 | 资源抽象单位 | 物理硬件 | Slot 可通过 slot 共享被多个算子复用，不是核数 |
| 有状态 vs 无状态算子 | 记住历史（存在状态里） | 只看当前输入 | 去重必须用有状态，否则跨批重复无解 |

### 6. 常见错误与注意事项

1. **"Spark 处理不了跨批重复"** ❌ → Spark 有状态去重可以做到，模板只是用了无状态 API。见下方薄弱点展开。
2. **把 Slot 当 CPU 核** ❌ → Slot 是内存+线程的抽象。
3. **"Flink 只能做流"** ❌ → Flink 名言"批是流的特例"，一套引擎流批一体。
4. **JM 只说"资源调度"** ❌ → 太窄，缺 JobGraph 解析、执行图切分、checkpoint 协调。
5. **面试答引擎对比用绝对化措辞**（"无法/不能"）❌ → 容易让懂行的面试官反杀，改用"代价/天花板"句式。

### 9. 思考题复盘

#### Q1：实时数仓为什么选 Flink 而不是 Spark Streaming？

**我的原始回答**：
> 因为前者是真正的实时数据处理毫秒级延迟，而后者是微批处理模拟实时，延迟是秒级，并且后者无法处理跨批重复问题（这里我有个问题，是Spark Streaming就处理不了跨批重复还是只是我们的模板项目没有处理重复）

**参考答案（四维结构）**：
1. 延迟：Flink 逐条处理毫秒级；Spark 微批延迟 ≈ 批间隔（秒级）。
2. 状态与可靠性：Flink 状态管理+checkpoint→exactly-once 原生保证；Spark 依赖 WAL 重放+外部幂等。
3. 乱序处理：Flink 事件时间+watermark 流式原生；Spark 事件时间窗口在批边界才触发，乱序数据要等批边界，延迟和准确性有天花板。
4. 生态：Flink 是国内大厂实时数仓事实标准。

**正确的部分**：① 真流毫秒 vs 微批秒级，机制判断准确；② 敏锐地发现了"跨批重复"这个核心差异点，而且**主动质疑了自己的说法**——这种自我追问很值钱，面试里也建议保持。

**错误、不完整或含糊的部分**：
1. "后者无法处理跨批重复"——**不准确**。Spark 有状态去重可以跨批去重，模板项目只是用了无状态 `dropDuplicates(["id"])`。
2. 缺了状态管理/exactly-once、乱序处理、生态三个维度，只答了延迟 + 去重两点。
3. 没有结合本项目例子（原版 `trigger(30s)` + `dropDuplicates` 两行代码即可佐证）。

**错误的具体原因**：把"模板代码的写法缺陷"直接推断为"引擎能力缺陷"，混淆了"框架能做到"和"代码没用对"；对 dropDuplicates 有状态/无状态两种形式区分不清。

**本题实际考查的知识点**：微批机制；有状态 vs 无状态算子；Spark/Flink 能力边界；面试对比类问题的回答结构（多维度+举例）。

**正确的分析思路**：先说结论（选 Flink 的 4 个维度）→ 每个维度对比两者机制 → 落到本项目代码佐证 → 最后可以主动补一句"Spark 也不是做不到，只是代价和粒度不同"，显得思考周全。

**以后遇到同类问题怎么判断**：先问自己"这是引擎能力问题还是代码写法问题"；涉及去重先说"有状态还是无状态"；说"无法/不能"之前，先想"是真的做不到，还是实现得不够好"。

#### Q2：微批和真流处理的本质区别？各自适合什么场景？

**我的原始回答**：
> 微批处理就把一段较小的时间间隔内的数据作为一批数据，一次处理一批数据，而真流处理是每条数据都做到实时处理

**参考答案**：微批 = 攒数据→切批→当批跑完→再攒，延迟 ≈ 批间隔；真流 = 来一条处理一条。微批适合吞吐优先、延迟不敏感的场景（批量报表、T+N 分析）；真流适合延迟就是钱的场景（实时风控、实时调价、实时监控）。

**正确的部分**：两种机制描述准确（攒一段→一批处理 vs 逐条处理）。

**错误、不完整或含糊的部分**：只答了"本质区别"一半，**"各自适合什么场景"整半题没答**。

**错误的具体原因**：回答时注意力只放在机制对比上，丢了题干的另一半问题——这是考试/面试里常见的丢分模式：题目有两问，只答了第一问。

**本题实际考查的知识点**：微批/真流的机制差异、适用场景判断（延迟敏感性）。

**正确的分析思路**：题干有两问就分两段答，先机制后场景；场景判断抓住一个关键词：**业务对延迟敏不敏感**。敏感→真流，不敏感→微批。

**以后遇到同类问题怎么判断**：答题前先把题目拆成几个问句，逐问作答；涉及"适合什么场景"时，用"延迟是否敏感 + 吞吐要求"两个维度判断。

**变式练习 Q2-1**：
> 某公司每天晚上跑一次全量报表，明天早上 8 点前出数即可，用流处理还是批处理/微批？如果业务是"用户刚下的订单必须在 5 秒内触发风控拦截"呢？为什么？

#### Q3：JobManager 和 TaskManager 分别负责什么？slot 和并行度什么关系？

**我的原始回答**：
> 前者负责整个数据处理的资源调度，断点设置，故障恢复等，后者负责真正的数据处理

**参考答案**：
- JobManager 完整职责：接收 Client 提交 → 解析作业成 JobGraph → 切分执行图 → 分配任务到各 TM 的 slot → 协调 checkpoint（保存点）→ 故障恢复。
- TaskManager：真正执行算子、处理数据、维护算子状态，内部按 slot 划分资源。
- Slot 与并行度：Slot 是 TM 里的资源单位（内存+线程的抽象）；**并行度 = 用多少个 Slot 同时干活**；算子的并行度不能超过可用 slot 数。

**正确的部分**：TM 职责正确；JM 提到"故障恢复"方向对。

**错误、不完整或含糊的部分**：
1. **完全漏答了"slot 和并行度什么关系"**——题干后半问没答。
2. JM 说"资源调度"太窄，缺 JobGraph 解析、执行图切分、任务分配、checkpoint 协调。
3. "断点设置"是口语，面试应该用"协调 checkpoint（检查点）"。

**错误的具体原因**：只记住了角色分工的大方向，没有把 JM 的完整流程背下来；对资源模型（slot/并行度）没有形成概念。

**本题实际考查的知识点**：Flink 架构三角色完整职责；资源模型（slot 是资源抽象、并行度与 slot 的约束关系）。

**正确的分析思路**：角色题按"流程+职责"背：JM 背五步（提交→JobGraph→执行图→分配→checkpoint/恢复），TM 背"执行算子+处理数据+维护状态"，资源题抓住一句"并行度是几，就有几个 slot 同时干；slot 不够，并行度再大也白搭"。

**以后遇到同类问题怎么判断**：架构题先按角色答，再补资源模型；题干出现两个名词（slot、并行度）时，明确回答"关系"，而不只是各自定义。

#### 薄弱点 A：有状态 vs 无状态去重（尚未掌握 → 当场纠正，待验证）

**我具体错在哪里**：说"Spark Streaming 无法处理跨批重复"。实际是模板项目用了无状态 `dropDuplicates(["id"])`，跨批重复是**代码写法**造成的，不是引擎能力边界。

**正确理解是什么**：
- 无状态算子：只看当前输入（当前这一批），不记得以前见过什么 → 跨批重复漏掉。
- 有状态算子：把见过的 id 记在**状态**里（Flink 是 KeyedState，Spark 是 checkpoint 状态），新数据来了先查状态，见过的就丢 → 跨批去重。
- Spark 有状态去重**可以做到**跨批去重；Flink 的差异在于状态更新是**逐条**的（毫秒级），Spark 是**以批为单位**刷状态（秒级），以及乱序处理（watermark）是流式原生。

**为什么容易出错**：看到模板代码有缺陷，就直接推断引擎不行——把"代码没用对"当成"框架做不到"。另一个原因是不了解 Spark 也有状态算子。

**正确与错误思路对比**：

| 错误思路 | 正确思路 |
|---|---|
| 模板项目去重失效 → Spark 引擎无法跨批去重 | 模板项目用了无状态 API → 是写法缺陷；引擎层 Spark 能做，粒度粗 |
| Flink 对比 Spark 说"它能做到所以选它" | 说"两者都能做，但 Flink 逐条更新、原生事件时间，代价和粒度更优" |

**一个简单例子**：30 秒一个批。消息 X 在 14:00:00.1 和 14:00:30.05 各来一次（被批边界切开）。无状态去重：两个批各看各的，两条都写出去 → 重复；有状态去重：第二批来的时候查状态发现 X 见过 → 丢弃 → 只写一条。

**一个容易设陷阱的例子**：面试官问"Spark Streaming 能做到 exactly-once 吗？"如果答"不能"，就踩坑了。正确答法：**可以**，通过 WAL 重放 + 幂等 sink 实现，但恢复依赖重放、状态更新是批粒度；Flink 的 checkpoint 是引擎原生快照，恢复几乎不重放，代价更低。关键在"也能做到，但代价不同"。

**一句便于记忆的判断口诀**（不能代替原理）：**"无状态只看眼前这一批，有状态记住所有见过的。"**

**后续复习建议**：① 做变式题 Q1-1；② 第 2 讲学完 watermark 后回看此题，把"跨批重复的彻底解法"补进答案；③ 第 4 讲学完状态管理后，用"KeyedState 怎么存储、怎么恢复"再验证一次。

#### 薄弱点 B：Slot 与并行度关系（尚未掌握 —— 漏答）

**我具体错在哪里**：Q3 只答了角色分工，完全没回答"slot 和并行度什么关系"。

**正确理解是什么**：Slot 是 TM 内部的资源单位（内存+线程的抽象，**不是 CPU 核**）；一个 TM 可以配多个 slot；**并行度 = 同时用多少个 slot 干活**，算子并行度不能超过可用 slot 总数（并行度 8 的作业至少需要 8 个 slot）。

**为什么容易出错**：答题时注意力被"角色分工"带走，漏了题干第二问；另外容易把 slot 和 CPU 核混为一谈（Flink 1.10+ 默认一个 slot 占一核，容易产生"slot=核"的错觉）。

**正确与错误思路对比**：

| 错误思路 | 正确思路 |
|---|---|
| slot = CPU 核 | slot 是资源抽象，可被多个算子的 task 通过 slot 共享复用 |
| 并行度 = 算子数量 | 并行度 = 同一算子并发实例数 = 占用的 slot 数 |
| 只答定义不答关系 | 必须点出"并行度 ≤ 可用 slot 数"这个约束关系 |

**一个简单例子**：2 个 TM × 每个 4 slot = 8 个 slot。并行度 6 → 可以跑；并行度 10 → 超出 8 个 slot，作业等待或拒绝。

**一个容易设陷阱的例子**：面试官说"Flink 1.10+ 默认每个 slot 占一个 CPU 核，所以 slot 数 = 核数，对吧？"——错。slot 是内存+线程的资源抽象，一个 slot 里可能串起多个算子的 task（slot 共享），只是默认模式下每 slot 用一核执行。

**一句便于记忆的判断口诀**（不能代替原理）：**"并行度是几，就是几个 slot 同时干；slot 不够，并行度再大也白搭。"**

**后续复习建议**：① 做变式题 Q3-1；② 第 6-7 讲部署时（YARN/K8s 内存规划）结合 `taskmanager.numberOfTaskSlots` 配置再理解一次。

## 四、第二讲：时间语义与 Watermark

### 1. 本讲主题和学习目标

主题：流处理的时间问题——事件时间、乱序与 watermark（本项目 4 个改造亮点中第 1 个的理论核心）。
目标：① 能答"为什么实时数仓必须用事件时间"；② 讲清 watermark 原理、生成方式与"永不后退"；③ 知道本项目怎么配置（30 秒容忍度）。

### 2. 核心概念及通俗解释

- **事件时间（Event Time）**：事件真正发生的时间，由数据自己携带（如埋点里的 `ts` 字段）。回答"这件事什么时候发生的"。
- **处理时间（Processing Time）**：数据到达 Flink 时机器自己的墙钟。回答"Flink 什么时候处理到它"。
- **乱序**：事件到达 Flink 的顺序 ≠ 发生顺序。来源：网络延迟、重试、Kafka 多分区、上游批量发送。
- **Watermark（水位线）**：程序自己维护的一把时钟，声明"事件时间 < T 的数据已到齐、不会再来了"。由已见数据最大事件时间 - 乱序容忍度得出。
- **乱序容忍度（delay）**：愿意等的最大乱序时间，是"延迟 vs 丢数据"的权衡参数。
- **迟到数据**：事件时间 < watermark 时才到达的数据（已错过安全关窗点）。

### 3. 重要原理与执行过程

**watermark 生成公式（必背）**：
```
watermark = max(所有已见数据的事件时间) - 乱序容忍度
```
- 数据每来一条都可能让 watermark 上涨；默认每 200ms 周期更新一次（也支持逐条更新）。
- **单调递增、永不后退**，两层保证：
  1. 事件时间本身不会倒流（业务时间语义）；
  2. Flink 实现层强制取 max(旧水位线, 新计算值)，防止后退。
- **窗口触发条件（第 3 讲展开）**：watermark ≥ 窗口结束时间 → 窗口触发计算。

**代码写法**（两种 API 都要认识）：
```java
// DataStream
stream.assignTimestampsAndWatermarks(
    WatermarkStrategy.<Event>forBoundedOutOfOrderness(Duration.ofSeconds(30))
        .withTimestampAssigner((event, ts) -> event.getTs()));
```
```sql
-- Flink SQL
WATERMARK FOR ts AS ts - INTERVAL '30' SECOND
```

### 4. 典型例子及分析过程

**点击归窗例子（必背，Q1 变式题要用）**：
- 用户 10:00:59 点击广告，事件携带 `ts=10:00:59`；网络抖动，10:03 才到 Flink。
- 处理时间 → 算进 10:03 窗口 ✗（时间归属错误，指标错误）
- 事件时间 → 看 ts 字段，算进 10:00 窗口 ✓

**本项目映射**：CSV 回放 → Kafka 多分区 → 乱序必然发生。容忍度设 **30 秒**（= 原版一个微批的长度，面试话术："我们的容忍度就是原版一个批的长度"）。原版 Spark 用 `processingTime="30 seconds"` 微批，**根本没使用事件时间**，乱序数据必然归错窗口——这就是改造亮点 1 的完整论证链。

### 5. 易混概念对比

| 对比项 | A | B | 关键区别 |
|---|---|---|---|
| 事件时间 vs 处理时间 | 数据自带，回答"何时发生" | Flink 墙钟，回答"何时到达" | 结果是否确定、时间归属是否准确 |
| watermark vs 数据里的时间戳 | 程序算出的时钟 | 业务字段 | watermark 是推导值，不是数据字段 |
| 乱序容忍度 0 vs 60 秒 | 低延迟但丢迟到数据 | 少丢数据但结果晚出 | 延迟与数据完整性的权衡 |
| 迟到 vs 乱序 | 晚到但还在容忍度内 | 到达顺序错乱 | 乱序是原因，迟到是相对 watermark 的状态 |

### 6. 常见错误与注意事项

1. **说"watermark 会后退"** ✗ → 永不后退，否则已触发的窗口无法保证正确。
2. **"乱序容忍度越大越好"** ✗ → 越大结果越晚（窗口要等 watermark），状态保留更久、内存压力更大。
3. **"处理时间完全没用"** ✗ → 吞吐压测、不关心时序的场景（简单计数）可以用，延迟最低。
4. **"watermark 就是数据里的时间戳"** ✗ → 它由已见数据的最大事件时间推导，是程序时钟。
5. **处理时间的风险只答"不一致"**（含糊）✗ → 要答到机制：时间归属错误 → 窗口归类错误 → 指标错误。

### 7. 本讲知识之间的联系

- **兑现第 1 讲的承诺**：第 1 讲说 Flink 乱序处理生态成熟，本讲给出机制（watermark）。
- **支撑第 3 讲**：窗口触发条件 = watermark ≥ 窗口结束时间。
- **引出第 5 讲**：迟到数据（allowedLateness、侧输出流）是本讲"容忍度之外的兜底"。
- **串联项目**：改造亮点 1（事件时间+watermark+状态去重）的"事件时间+watermark"部分已讲完，"状态去重"留到第 4 讲。

### 8. 本讲速记

- 公式：**watermark = max(已见事件时间) - 容忍度**
- 三不：**永不后退、默认 200ms 更新、窗口等 watermark**
- 口诀：**事件时间看"发生了没"，处理时间看"到了没"**
- 口诀：**容忍度是权衡：等得越久越全，但越晚出结果**
- 本项目：事件时间 = 埋点 ts；容忍度 30 秒；原版 Spark 用 processingTime → 归窗必错

#### Q2：watermark 是什么？怎么生成的？为什么它"永不后退"？

**我的原始回答**：
> watermask是一个时间戳，它是由flink结合当前已到达数据的最大时间戳和系统容忍度计算得出的，因为它的计算方式是max（已到达数据的时间戳）- 系统容忍度，这就决定了它是单调递增的

**参考答案**：watermark 是程序维护的时钟，声明"事件时间 < T 的数据已到齐"。生成：`watermark = max(已见事件时间) - 乱序容忍度`，Flink 默认每 200ms 周期更新。永不后退的两层保证：① 事件时间语义上不会倒流（数据只会更晚发生，不会更早）；② 实现层强制取 `max(旧水位线, 新计算值)`。

#### Q3：乱序容忍度设 0 秒和设 60 秒，各会有什么后果？

**我的原始回答**：
> 设置0秒意味着系统对乱序到达的数据没有容忍度，乱序是flink数据的常态，会导致大量数据被直接遗弃而对后续业务产生影响，设置60秒会导致系统延迟等待时间过长

**参考答案**：
- 0 秒：watermark 紧跟已见最大值，任何晚到数据都成为迟到数据，默认被丢弃（无兜底时）→ 乱序程度高时丢数据多、指标不准。
- 60 秒：窗口触发要等 watermark ≥ 窗口结束时间，**结果可见性延迟 ≈ 容忍度 + 窗口时长**（一个 10:00-10:01 的窗口大约 10:02:00 才出结果）；状态保留更久，内存压力大。换来的是对乱序的容忍，数据更完整。

**正确的部分**：0 秒丢数据、60 秒延迟大的**方向正确**，权衡的直觉是对的。

**错误、不完整或含糊的部分**：
1. "大量数据被直接遗弃"表述不精确——精确说法：**事件时间 < watermark 之后到达的算迟到，默认丢弃**（丢多少取决于乱序程度，不是必然大量）。
2. 60 秒只答"延迟等待过长"——缺**窗口触发机制**：结果可见延迟 ≈ 容忍度 + 窗口时长；缺**状态开销**：状态保留更久。

**本题实际考查的知识点**：容忍度对窗口触发延迟的影响机制；状态生命周期；权衡思维。

## 五、第三讲：窗口

### 1. 本讲主题和学习目标

主题：窗口是"流上做聚合"的载体——把无界流切成有界片段计算。
目标：① 能答三类窗口的定义、区别与选型；② 讲清触发条件（watermark ≥ 窗口结束时间）；③ 掌握迟到数据三层兜底（容忍度 → allowedLateness → 侧输出流），兑现第 2 讲"watermark 之后才到的数据"的承诺。

### 2. 核心概念及通俗解释

- **滚动窗口（Tumbling）**：固定长度、不重叠、不滑动，一条数据只属于一个窗口。例：每隔 1 分钟统计点击数。
- **滑动窗口（Sliding）**：固定长度 + 固定步长，步长 < 长度时窗口重叠，一条数据属于多个窗口；步长 = 长度退化为滚动窗口。例：统计最近 10 分钟指标、每 5 分钟刷新一次 → 窗口长度 10 分钟、步长 5 分钟。
- **会话窗口（Session）**：长度不固定，按相邻事件间隔切分，一次连续行为属于一个窗口。例：分析一次完整的用户访问会话。
- **窗口触发条件（必背）**：**watermark ≥ 窗口结束时间 → 窗口触发计算**。容忍度越大，触发越晚。
- **迟到数据三层兜底（递进关系）**：
  1. **乱序容忍度**：全局等待——watermark = max(已见事件时间) - 容忍度，容忍度之内的乱序数据天然进入正确窗口；
  2. **allowedLateness**：局部补算——窗口触发计算后仍保留该窗口一段时间，此期间到达的数据再次触发窗口计算并把**更新后的结果**发给下游（默认丢弃旧结果、发新结果）；
  3. **侧输出流（side output）**：旁路处理——错过 allowedLateness 后到达的极迟数据进侧输出流，留待人工/专门任务处理。

### 3. 重要原理与执行过程

**触发链条**：watermark 上涨 → 每个窗口检查"watermark ≥ 窗口结束时间？" → 满足则触发计算并输出 → 窗口关闭（允许 allowedLateness 期间补算）。

**三层兜底对比**：

| 层 | 机制 | 全局/局部 | 数据还能进主链路吗 |
|---|---|---|---|
| 容忍度 | 推迟 watermark，等待乱序 | 全局（所有窗口） | 是（正常计算） |
| allowedLateness | 窗口触发后保留一段时间补算 | 局部（单个窗口） | 是（二次计算重发结果） |
| 侧输出流 | 极迟数据旁路 | 局部 | 否（进侧流待处理） |

### 4. 典型例子及分析过程

- **滚动窗口**：每分钟点击数 → 1 分钟滚动窗口，一次触发输出一条。
- **滑动窗口**："最近 10 分钟、5 分钟刷新" → 10 分钟长度 + 5 分钟步长，同一时刻有 2 个活动窗口；ts=09:58 的数据同时属于 09:50-10:00 和 09:55-10:05 两个窗口。
- **会话窗口**：用户 10:00 打开 App、10:02 浏览、10:20 又打开 → 按静默间隔切成两个会话。

### 5. 易混概念对比

| 对比项 | A | B | 关键区别 |
|---|---|---|---|
| 窗口时长 vs 步长 | 窗口覆盖多长 | 多久开一个新窗口 | 滑动窗口 S<L 重叠；S=L 退化为滚动 |
| 窗口参数 vs 容忍度 | 决定多久出一份结果 | 决定乱序数据等多久 | 出结果频率调窗口；等迟到调容忍度 |
| 滚动 vs S=L 的滑动 | 不重叠 | 形式上重叠=0 | 数学上等价，只叫法不同 |
| allowedLateness vs 容忍度 | 窗口触发后局部补算 | 触发前全局等待 | 一个管"关窗后"，一个管"关窗前" |
| 允许迟到 vs 侧输出 | 还进主链路补算 | 进旁路 | 主链路结果仍会修正 vs 旁路需自行处理 |

### 6. 常见错误与注意事项

1. **"每 5 秒看到结果 = 容忍度设 5 秒"** ✗ → 出结果频率由**窗口时长/步长**决定；容忍度只管乱序等待，调大只让结果更晚。
2. **把 allowedLateness 当全局等待** ✗ → 它是"窗口已触发后的局部补算"，代价是每个窗口多保留一段时间 + 结果二次下发。
3. **滑动窗口重叠忘了"一条数据属于多个窗口"** ✗ → 跨窗口重复计数是滑动窗口的正常语义（按场景选型，不是 bug）。

### 7. 本讲知识之间的联系

- **承接第 2 讲**：触发条件就是 watermark ≥ 窗口结束时间；容忍度直接影响触发时刻。
- **引出第 4 讲**：窗口里攒的数据 = 状态的一部分；窗口计算中挂了怎么办 → checkpoint 保证不丢。
- **兑现第 2 讲承诺**：allowedLateness + 侧输出流就是"watermark 之后才到的数据"的兜底答案。

### 8. 本讲速记

- 口诀：**滚动不重不滑，滑动又重又滑，会话随缘切分。**
- 触发：**watermark 到点（≥窗口结束）才开闸。**
- 三层兜底：**容忍度全局等 → allowedLateness 局部补 → 侧输出旁路收。**
- 选型口诀：**固定周期用滚动；"最近 N 分钟刷新 M 次"用滑动；连续行为用会话。**

## 六、第四讲：状态与 checkpoint

### 1. 本讲主题和学习目标

主题：Flink 的灵魂——有状态计算与故障恢复（兑现第 1 讲"状态+checkpoint→exactly-once"）。
目标：① 能答 KeyedState vs OperatorState 及去重必须 keyBy；② 讲清 checkpoint 原理（Chandy-Lamport）与不阻塞原因；③ 掌握故障恢复流程；④ 分清"状态层面 exactly-once"与"端到端三件套"。

### 2. 核心概念及通俗解释

- **为什么需要状态**：去重（记得见过的 id）、窗口聚合（记得窗口里的数据）、维表缓存（记得查过的维度）——三件事都要"记得"。
- **KeyedState（键控状态）**：按 key 隔离的状态。keyBy 后相同 key 的数据到同一实例，每个 key 有自己的状态。类型：ValueState（单值）/ ListState（列表）/ MapState（字典）/ ReducingState / AggregatingState。**必须先 keyBy 才有 KeyedState**。
- **OperatorState（算子状态）**：不按 key、按算子实例记录。典型例子：**Kafka offset**（每个分区一个 offset）、批场景 ListState（分区文件列表）。
- **StateBackend（状态存储后端）**：内存（JVM heap，快但有限）→ 文件（Fs，可持久化）→ **RocksDB**（嵌入式 KV，存本地磁盘，LSM 树，支持超大状态，快照异步）。状态太大内存放不下 → RocksDB。
- **checkpoint**：定期把"当前状态"快照存到持久化存储，故障后可恢复。类比：日记每天都在写（状态实时更新），拍照备份每周一次（快照）。
- **exactly-once 三级别**：at-most-once（至多一次，可能丢）/ at-least-once（至少一次，可能重）/ exactly-once（恰好一次，不丢不重）。指标业务（金额、计数）必须 exactly-once。

### 3. 重要原理与执行过程

**Chandy-Lamport 异步屏障快照（对齐流程，必背）**：
```
场景：算子实例有 2 个上游通道 A、B
① JobManager 发起 checkpoint N，向所有并行 source 注入 barrier b
② barrier b 随数据流经各通道
③ 实例收到 A 通道的 b：不立即快照！暂停 A 通道后续数据（缓存），继续处理 B 通道
④ 等 B 通道的 b 也到达（B 在 b 之前的数据已处理完）→ 两通道到齐
⑤ 此时状态 = "截至 b 之前所有数据的效果"（一致快照）→ 快照存持久化存储
⑥ 快照完成，放开缓存的 A 通道数据，barrier 向后传
```
- 为什么对齐：不等齐就快照，有的通道是 b 前状态、有的是 b 后状态 → 快照不一致，恢复时错乱。
- 为什么不阻塞：快照复制的是状态（RocksDB 异步 / copy-on-write），主流不停；对齐只暂停"快的那条通道"（背压）。
- 代价场景：大状态/慢通道可改用 Unaligned Checkpoints（不对齐快照）——加分项。

**故障恢复流程**：TaskManager 心跳超时 → JobManager 检测到 → 重启任务 → 状态回滚到最近 checkpoint 时刻 + **从 checkpoint 记录的 Kafka offset 重放数据** → 窗口/聚合从断点续算，结果不丢不重。

**端到端 exactly-once 三件套（L4 核心，必背）**：
```
source 可重放（offset 存在状态里） + 状态快照（checkpoint）+ sink 幂等/事务（upsert 或两阶段提交）
```
- Flink 的 checkpoint 保证的是**状态层面** exactly-once；
- 端到端还要：source 知道从哪重放（否则漏/重）+ sink 重复写结果一致（否则下游重复行）。

### 4. 典型例子及分析过程

- **去重必须 keyBy**：重复事件 A 出现两次，若散到两个并行实例，各自状态都"没见过 A" → 都写出 → 重复；keyBy(A) 后两条都路由到同一实例，共享 MapState → 第二条查状态发现见过 → 丢弃。
- **Kafka offset = OperatorState**：每个分区一个 offset 记录在算子实例里（KafkaSource 并行度 = 分区数时一对一）。
- **本项目映射（简历素材）**：DWD 状态去重 = keyBy(event_id) + MapState（跨批/跨窗口去重）；维表缓存 = 维表数据放状态；ADS 幂等 upsert = 确定性主键 + 覆盖式写入（重放不重复累加）。

### 5. 易混概念对比

| 对比项 | A | B | 关键区别 |
|---|---|---|---|
| KeyedState vs OperatorState | 按 key 隔离 | 按算子实例 | 前者依赖 keyBy，后者不依赖 |
| 内存 vs RocksDB | 快、容量受限 | 慢一些、超大状态 | 小状态内存、大状态 RocksDB |
| checkpoint vs savepoint | 自动定期，故障恢复用 | 手动触发，升级/迁移用 | 生命周期不同 |
| 状态层 vs 端到端 exactly-once | 状态回滚+重放 | 还需 source/sink 配合 | 三件套缺一不可 |
| at-least-once vs exactly-once | 可能重复 | 不重不丢 | 重复输出是否被消除 |

### 6. 常见错误与注意事项

1. **"恢复 = 只回滚状态"** ✗ → 还要从记录的 offset **重放数据**，窗口才能续算。
2. **"端到端 exactly-once 只要 checkpoint"** ✗ → 三件套：source 可重放 + 状态快照 + sink 幂等/事务。
3. **"checkpoint 拍快照"不说明存哪** ✗ → 存到持久化存储（HDFS/本地文件/RocksDB），这是可恢复的前提。
4. **"去重不 keyBy 也行"** ✗ → 不 keyBy 状态不隔离，重复数据跨实例必重。

### 7. 本讲知识之间的联系

- **兑现第 1 讲**："状态管理 + checkpoint → exactly-once"是选 Flink 的第二大理由，本讲给出完整机制。
- **兑现第 3 讲**：铺垫题"窗口挂了会丢吗"→ 窗口数据=状态，checkpoint+重放保证不丢。
- **支撑项目**：状态去重、幂等 upsert、故障恢复演练（第 4 周简历素材）。

### 8. 本讲速记

- 口诀：**去重、聚合、缓存——三件事都要"记得"。**
- 口诀：**checkpoint = 定期拍集体照，挂了回到最近一张。**
- 三件套：**source 可重放 + 状态快照 + sink 幂等/事务。**
- 面试金句：**"Flink 的 exactly-once 是状态层面的；端到端要 source 可重放 + sink 幂等/事务。"**

**标准答案（重点薄弱点，完整背）**：
1. checkpoint 保证：状态回滚到快照时刻 + 从快照记录的位置**重放** → 状态结果等价于每条数据恰好处理一次（**状态层面** exactly-once）。
2. 端到端不够的原因：状态恢复了，但数据重新流过整个链路，**下游会收到重放的重复结果**：
   - **source 必须可重放**：Kafka offset 存在状态（OperatorState），恢复时从记录 offset 继续消费——否则不知道从哪重放（漏或重）；
   - **sink 必须幂等或事务**：状态重算后 sink 再次输出，普通 INSERT 写重复行 → 幂等（确定性主键 + upsert 覆盖）或事务（两阶段提交）；
   - **三件套：source 可重放 + 状态快照 + sink 幂等/事务**，缺一个端到端不成立。
3. 本项目配合：Kafka 可重放（offset 在状态）✅ + DWD 去重/DWS 窗口聚合（checkpoint 快照）✅ + ADS 写 MySQL 确定性主键覆盖式 upsert（重放不累加）✅。
4. 面试金句："Flink 的 exactly-once 是状态层面的；端到端要 source 可重放 + sink 幂等/事务。"

**判定：尚未掌握**（答"不知道"，以上为完整补课）。

#### Q4（回填铺垫题）：窗口计算中挂了会怎样？从状态和 checkpoint 角度完整回答。

**我的原始回答**：
> 不会丢,TaskManager挂了一段时间后会被检测到心跳超时,然后系统从最近的checkpoint回复状态,然后重启任务

**参考答案**：恢复流程主干对（心跳超时检测 + 最近 checkpoint + 重启）。

**错误、不完整或含糊的部分**：漏了最关键一环——**重放**。完整链条：
1. **窗口数据 = 状态的一部分**（存在 StateBackend），checkpoint 快照的就是它；
2. 恢复 = 状态回滚到 checkpoint 时刻 + **从 checkpoint 记录的 Kafka offset 位置重放数据**（offset 也在快照里）；
3. 重放后窗口从断点续算，不丢不重（状态层面 exactly-once）——兑现第 1 讲承诺。

**判定：基本掌握**（恢复主干对，补"窗口=状态 + 重放"两要素）。

### 10. 掌握程度判定与薄弱点重点展开

判定结果：Q1 基本掌握（keyBy 必要性验证改善）；Q2 理解不稳（缺对齐/存储）；Q3 **尚未掌握**（答"不知道"，已重点展开三件套）；Q4 基本掌握（缺重放）。

#### 薄弱点：端到端 exactly-once 三件套（尚未掌握）

**我具体错在哪里**：Q3 答"不知道"——只见过"checkpoint → exactly-once"的结论，没想过状态恢复后数据要重走全链路，下游会收到重复结果。

**正确理解是什么**：exactly-once 是"结果不丢不重"。状态快照只保证 Flink 内部状态一致；重放发生时（1）source 要能从断点继续消费（offset 在状态里），（2）sink 要能接受重复写而不产生重复行（幂等 upsert 或事务）。三件套缺一，端到端就不成立。

**为什么容易出错**：把"Flink 的 exactly-once"当成引擎全包；实际上 Flink 只承诺状态层面，端到端是工程配合问题。

**一个简单例子**：作业算 PV，故障重放后窗口重算一次，下游若普通 INSERT 会写两条同样的 PV 记录 → 指标翻倍；用确定性主键（metric_date+window_start+metric_name+维度）upsert，重放只覆盖同一行 → 值不变。

**一句便于记忆的判断口诀**：**"三件套：source 记得从哪重放，状态记得回滚到哪，sink 记得写重复了也不怕。"**

**后续复习建议**：① 背三件套 + 本项目映射（Kafka offset / checkpoint / MySQL upsert）；② 第 4 周故障演练（kill TM）时实地观察恢复+重放，面试可讲"我验证过"。
