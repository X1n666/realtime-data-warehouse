> 用法：面试前 10 分钟扫一遍。**第 1 节**用于开场自我介绍，**第 2 节**每一格对应一个"可讲的坑"，**第 3 节**是深挖问答，**第 4 节**是诚实清单（别吹过头，被追问会翻车）。

## 1. 一分钟主线（开场用）

> "我先用 Docker 搭了 MySQL/Kafka/Flink 环境，**用生成器造出可重现的三阶段交易数据**（这是能对账的前提）；然后**竖切一条最小链路**跑通 ODS→DWD→DWS→ADS；接着接入支付/退款/下单 CDC 建交易域，并**用批 SQL 做流批对账**，做到日口径指标分毫不差；再把作业**拆成物理四层**、上 Grafana；补分钟层时踩了一个**事件时间乱序导致水位跳变、窗口大面积不触发**的坑，用分层排查法定位并重放修复；最后用 Lookup Join 补上**维度建模**（分省 GMV、分品类金额，求和能回到日锚点，顺带证明 join 基数正确），作业数到 14。收尾时又抓到一个最阴的：**Kafka 保留期把源 topic 静默删空**——topic 还在、消费组 lag 全 0、作业全 RUNNING、看板数字还全对，只是源数据没了；发现时距它把整个 Kafka 层删光只剩 79 分钟，抢救回来后把冷启动恢复链做成了一条命令。全程记录在开发日志，已开源。"

**主线七个字**：搭环境 → 竖切跑通 → 接交易域 → 对账证明数对 → 分层工程化 → 深水区排障 → 闭环交付。

## 2. 七步主线 · 每步一个可讲的坑

| 步骤 | 做了什么 | **可讲的坑 / 亮点** |
| --- | --- | --- |
| ① 环境与数据底座 | Compose 起 MySQL(binlog ROW+FULL+30d)/Kafka/Flink/Grafana；9 张业务表；三阶段交易生成器 + 行为日志生成器 V2 | **数据可重现是能对账的前提**——同 seed 重放结果一致，批侧才算得出同一个数。随机造数的人对不了账 |
| ② 竖切最小链路 | ODS→DWD(去重)→DWS(1min 窗口 PV)→ADS(MySQL) | `ROW_NUMBER` 去重输出的是 **changelog**，append sink 编译报错 → 必须用 **upsert-kafka** 承载 |
| ③ 交易域接入 CDC | 支付 / 退款 / 订单明细 三条 CDC 支线 + 日聚合 | ① CDC 要显式 `server-time-zone=Asia/Shanghai`（否则 +8 vs Etc/UTC 时区校验失败）② **多作业必须分段 server-id**，否则互相踢下线 ③ **日聚合用 `GROUP BY CAST(ts AS DATE)` 而非窗口**——窗口要求事件时间单调，而 CDC 快照按主键扫描、天生乱序 |
| ④ 批流对账闭环 | 每指标用批 SQL 独立算一遍，流批逐值比对 | ① **红线：日 PV/UV 必须独立重算，禁止 `SUM(分钟)`**（分钟之和 ≠ 日值）② 主动解释"分钟 636 vs 日 641"是**尾部未触发窗口的预期差异**，不是 bug——**能区分"已知差异"和"未知 bug"是数据质量的核心能力** |
| ⑤ 分层 + 可视化 | 拆成物理四层 14 作业（含 2 个维度作业）；Grafana provisioning 声明式注册 | **同一个 SQL 文件里的多个 INSERT = 多个独立作业**（Flink SQL 特性），但它们会共享 source 的 `group.id` → **partition 被一个作业独吞、另一个空转**。踩了两次，教训：**每新增一个 INSERT 分支，就必须再立一份 source DDL + 独立 group.id** |
| ⑥ 分钟层 + 深水区排障 | 补分钟 UV、交易分钟表；看板补分钟层 | **全项目最值钱的 bug**：CDC 快照按主键扫描输出 + 测试数据 id 与时间错位 → topic 内**事件时间乱序** → upsert-kafka 水位按物理消费序推进，**先读到晚事件后，其后所有早事件被判迟到丢弃** → 窗口只 fire 了 43 个就停。<br>**分层排查法**：非窗口日聚合对账正确 → 怀疑窗口 → 临时无窗口统计验证全量 ✓ → dump topic 时间序列看到乱序 → 定位到机制层。<br>**修复**：一次性按时间序**重放**成"真实事件流" |
| ⑦ 闭环 + 工程化 | 订单明细 CDC 补全生命周期；`start_env.sh` 一键启动（`--full` = 冷启动恢复链）；开源发布 | ① **作业风暴**：提交命令误执行两次 → 同 server-id 的 CDC 作业互踢 → 15 个作业 RESTARTING 循环，cancel 与 restart 赛跑清不掉 → 正确恢复 = **重启 jobmanager**（standalone 无 HA，作业全灭但 Kafka/MySQL 数据不丢）→ 按依赖序重提。教训：**恢复用"全灭重建"而不是逐个 job cancel** ② GitHub **100MB 限制对历史对象同样生效**——只 `git rm --cached` 不够，得重写历史 ③ **保留期静默删源数据**（全项目危害最大，见 Q7 第二幕）+ 冷启动恢复链自动化（见 Q7c） |

## 3. 深挖问答（面试官追问时用）

### Q1：你的 checkpoint 怎么配的？怎么证明容错生效？
- 配置：`execution.checkpointing.interval = 30s`、`state.checkpoints.num-retained = 3`。
- **配置了 ≠ 验证了**。诚实的答法是："配置是 X；恢复演练我做了/还没做（见第 4 节）"。
- **可延伸（本项目实测数据）**：`GET /jobs/<jid>/checkpoints` 拿到真实值——四类作业 checkpoint 耗时 **3–12 ms**、体积最大 ~0.6 MB；间隔 30s 时 `completed` 计数稳定增长、`failed=0`，这是"checkpoint 机制在正常工作"的直接证据。
- **checkpoint 间隔是吞吐与恢复时间的权衡**：间隔小恢复快但开销大；间隔大开销小但故障后重放的数据多。

### Q1b：你的 checkpoint 存在哪儿？（**答这题能看出是不是真跑过**）
很多人只答得出"间隔/超时"，答不出**存储位置**。本项目的运行时真值（`/jobs/<jid>/checkpoints/config`，不是文档抄的）：

```
state_backend         = HashMapStateBackend       ← 状态在 TM 堆
checkpoint_storage    = FileSystemCheckpointStorage ← checkpoint 落盘（2026-09-16 修复后）
state.checkpoints.dir = file:///opt/flink/checkpoints（JM/TM 挂同一命名卷）
```

**修复前是另一个答案，而"我怎么发现并修掉它"比结论本身值钱**：

- 修复前 `checkpoint_storage = JobManagerCheckpointStorage` + `state.checkpoints.dir` 未配置 + jobmanager 无持久化卷 → **checkpoint 元数据和状态字节全在 JM 堆内存**，JM 一丢全丢、无从 restore；standalone 又无 HA，JM 重启后作业不会自动拉起。
- **再深一层（很少人知道）**：`JobManagerCheckpointStorage` 用 `MemCheckpointStreamFactory` 写状态，`checkSize()` 超过 `DEFAULT_MAX_STATE_SIZE = **5 MB**` 会**直接抛 IOException 让 checkpoint 失败**（不是告警）。当前实际值 ~0.6 MB 很安全，但**去重状态一旦增长就会撞崖**——正好接上 Q2 的 TTL 话题。
- **修法**：设 `state.checkpoints.dir`（存储自动切 `FileSystemCheckpointStorage`）+ JM/TM 挂同一命名卷同路径。**踩到的 Docker 坑**：Docker 给"镜像里不存在的路径"建挂载点时属主是 `root:root/755`，而 flink 镜像的 entrypoint 会把 PID 1 降权到 `flink` → 建 checkpoint 目录 EACCES，作业报 `Failed to create directory for shared state`。
  **假阳性陷阱**：`docker exec` 进去手测 `mkdir` 会成功（exec 默认 root、绕过 entrypoint），很容易误判"权限没问题"——**必须 `ps` 看 PID 1 的真实用户**。修法是加一次性 init 容器 `chown`，且**必须覆盖 entrypoint**，否则 chown 也以 flink 身份跑（`Operation not permitted`）。
- **验证方式**（不只看配置）：`/jobs/<jid>/checkpoints/config` 显示 `FileSystemCheckpointStorage`，且卷里真有 `chk-N/_metadata` 文件。
- **但要诚实说**：存储位置修好了 ≠ 恢复演练做过。当前恢复手段仍是**无状态全量重算 + 幂等覆盖写**，从 checkpoint restore 的完整链路**还没演练**（见第 4 节）。

### Q2：你的状态会不会无限增长？TTL 怎么设？
**这是本项目的加分题**，答错很常见：

- **开源 Flink 的 `table.exec.state.ttl` 默认值是 `0` = 永不过期**（官方描述原文："Default value is 0, which means that it will never clean up state."）。**阿里云 VVR ≥4.0.12 默认是 1.5 天**——**两边不一样，别答混**。
- 项目里**按"状态是否有界"分类处理**：
  - **job1 的 `event_id` 去重状态 = 无界**（∝ 累计去重键数）→ 必须显式设 `table.exec.state.ttl = 24h`；
  - **job2 的窗口状态**：窗口 fire 后自动清理 → 不需要 TTL；
  - **job2 的日聚合状态 = 有界**（∝ 日期 × 指标基数）→ **刻意不设 TTL**。
- **为什么不给日聚合设 TTL**（说得出这条很加分）：它的 `COUNT(DISTINCT uid)` 保留去重集合，若 TTL 过短，迟到数据到达时状态已被清理 → 聚合**从零重算，写出错的日指标**（可能报 `Can not retract a non-existent record`）。**TTL 不是越短越好——取值必须小于业务可接受的重算窗口。**

### Q3：你的链路是端到端"精确一次"吗？
**答"是"就露馅了。** 正确答法：
- Kafka 侧开 checkpoint 后 sink 走**两阶段提交**，链路内 exactly-once；
- 但 MySQL sink 用的是 JDBC **幂等写**（`ON DUPLICATE KEY UPDATE`）→ 整体是 **at-least-once 投递 + 幂等落库**；
- 因为最终形态是**按主键覆盖**，重复消费不产生重复指标——**用幂等性换取了不引入 2PC 的复杂度**。这也是我故障恢复时敢用"全量重算 + 覆盖写"的依据。

### Q4：多个 source 时水位怎么推进？某个源没数据会怎样？
- 作业水位 = **所有 source 水位的最小值**。某个 source 长时间无数据，它不推进 → **会拖住整个作业**，导致下游窗口不触发。标准解法是 `table.exec.source.idle-timeout`（默认 `0` = 关闭）。
- **但要讲清代价**：源被标记 idle 后水位可前冲，之后到达的（略晚的）数据会被判迟到丢弃。**该值要结合数据到达节奏定**，本项目流量是突发型生成，所以没有贸然开启。

### Q5：并行度怎么定的？
- 本项目**并行度 = 1、topic 分区数 = 1**，这是单机资源下的合理取舍。
- **但要能答出约束**：*"source 的并行度受**分区数**上限约束——1 个分区时并行度设 8 也只有 1 个 subtask 在消费。要提吞吐得先扩分区再提并行度，同时注意扩分区会改变 key 的分区规则。"*

### Q6b：维度建模怎么做的？Lookup Join 踩过什么坑？（**本项目的"下一步"已经落地成代码**）
- **场景不是"想用 Lookup Join"而是"只能用"**：DWD 层没有 order_info 流（只接了 payment/refund/order_detail 三条 CDC），而 `province_id` 只存在于 MySQL 的 order_info 里 → 分省指标必须 lookup 补这一跳。
- **两条硬约束（实测报错，不是背书）**：
  1. `FOR SYSTEM_TIME AS OF` **只能引用左表的时间属性**——直接写事件时间列会报 `Temporal table join currently only supports 'FOR SYSTEM_TIME AS OF' left table's time attribute field`。
  2. 给左表加水位后仍然不行：`Event-Time Temporal Table Join requires both primary key and row time attribute in versioned table, but no row time attribute can be found` → **JDBC 维表不是"版本表"，事件时间 temporal join 根本用不了，只能配 `PROCTIME()`**。想要事件时间版本语义，维表本身得是带 rowtime 的 changelog 流（CDC 维表）。
- **PROCTIME 的额外好处（这层想到的人不多）**：它**不需要水位** → 作业可以安全消费事件时间非单调的 topic（正是节点8 那个坑的根源）。而且理由更本质：**JDBC lookup 本来就是"处理时刻点查"，没有按事件时间取历史版本的能力，硬套事件时间语义是假的精确。**
- **链式 lookup 可行**（`payment → order_info → base_province` 编译成两层嵌套 LookupJoin），聚合仍是 retract 流 → 必须 upsert-kafka 承载。
- **缓存权衡**：`lookup.cache.max-rows` 封顶 + `lookup.cache.ttl` 是"最长不一致窗口"；维表越稳定（省份几乎不变）越能放大缓存，越易变（商品价格）越要缩短 ttl 或改走 CDC 维表。
- **最漂亮的一点——维度指标自带完整性校验**：`SUM(分省 GMV)` 必须回到日锚点 1,136,485.35、`SUM(分品类下单金额)` 回到 1,334,596.00。**维度求和回锚点等价于证明了 join 基数正确**：维表未命中会丢行（和偏小）、维表一对多会膨胀（和偏大）。这是"加维度不改口径"的证明。

### Q6：为什么 DWD/DWS 用 upsert-kafka，ADS 用 MySQL？
- DWD/DWS 是**变更流**（去重/聚合产生 update/delete 语义），append 模式表达不了 → upsert-kafka 按主键覆盖；
- ADS 是**面向查询的结果层**，需要 MySQL 提供低延迟点查给 Grafana → `ON DUPLICATE KEY UPDATE` 覆盖写。

### Q7c：环境怎么保证"随时能重建"？（可复现性是数据岗的硬要求）
数据源在两个地方，**两处都得先重建再启作业**，且顺序有依赖（`start_env.sh --full` 一条命令串起来）：

```text
① MySQL 源库      load_mysql_source.sh      交易域唯一数据源；空库 = 全链路静默零指标
② 流量源 topic    replay_traffic.sh         确定性重放 2000 行（同 seed 两次 md5 逐字节一致）
③ 只提 job1      —— 两条源链的共同上游（流量加工 + CDC 全量快照）
④ 等源链灌出     dwd_traffic_event ≥2000 且 dwd_payment_detail ≥182（各等稳定 10s）
⑤ 重排交易 topic  replay_dwd_payment_sorted.sh  必须在提交下游作业**之前**做
```

- **⑤ 的顺序不是随便定的**：有消费者在线时 topic 删除永远完不成（auto-create 60s 一轮重建循环），无消费者时 **1 秒**生效——这是 Q7 第一幕那个坑的直接推论，被固化成了脚本顺序。
- **④ 的期望值容易被写错**：冷启动是 **2000 不是 12000**。job1 的 source 写死 `earliest-offset`，每提交一次就重放一遍全量 → topic 里累积 N 份历史副本（实测 12000 = 6 次 × 2000）；副本无害（下游 upsert 读法是"每 key 取最新"），但阈值必须按**单次重放量**写。
- **重放的忠实性可验证**：生成器自报 **browse=641**，与已验收日锚点 `browse_pv=641` 完全吻合 —— 证明是**忠实重建**，不是"随便造点数据把看板填满"。这正是"数据可重现是能对账的前提"的工程落地。
- **顺手修掉一个同类静默坑**：compose 原来挂的 MySQL init 目录 `./mysql-init` 是个**空目录**（且空目录不入 git，全新 clone 根本没有）→ 空卷首次启动会建出**空库**，CDC 无表可读、全链路静默零指标。现已把 4 个真实文件按 `01→04` 前缀挂进去，并在一次性容器里实测了三条路径（空库自动灌 / 非空拒绝重灌 / `--force` 清空后重灌），9 张源表行数与 manifest 逐项吻合。

### Q7：讲一次"最难查"的故障（**这题最分高下，答好能直接赢**）
背景：job4 的省份分支**一条输出都没有**，但作业**状态是 RUNNING、没有任何异常**。

**三次假设被证据依次推翻**——过程本身就是答案：
1. 假设"默认 `scan.startup.mode=group-offsets`，无提交位点时回退 LATEST" → 字节码里确有 `orElse(StartupMode.GROUP_OFFSETS)`。
2. 假设"那改成 `earliest-offset` 就能修" → **推翻**：TM 日志里明明是 `auto.offset.reset = earliest`、`Seeking to earliest offset`。
3. 假设"那 topic 里有数据、只是没读到" → **推翻**：`kafka-get-offsets.sh --time -2/-1` 显示 `earliest=182 latest=182`，**topic 是空的**，读 0 条**是正确行为**。

**真因在 broker 日志，不在 Flink 侧**——三层叠加的**静默空读**：
- ① `auto.create.topics.enable=true`（Kafka 默认）+ **订阅它的消费者在线** → 任何 metadata 请求都会把刚删掉的 topic **自动重建为空 topic**；
- ② topic 删除是**异步**的，实测本机耗时**整 60 秒** → 删除/重建/生产互相赛跑；
- ③ committed offset 落在新 topic 的合法区间内（正好 = 末尾）→ **不回退**。

**复现实验把归因钉死**：消费者在线时删除永远完不成（实测 60s 一轮的删除/重建循环）；`cancel` 掉订阅它的 4 个作业后**删除 1 秒完成**。

**为什么这题值钱**：
- **"存在但为空"比"不存在"危险得多**——不存在会报错，存在但为空会被 `earliest` 静默吞掉。凡是"缺失 ⇒ 静默降级"的系统，都要显式断言非空。我把这条写成了 `start_env.sh` 的**空 topic 哨兵**。
- **连带挖出一个更严重的隐患**：`docker exec gmall_kafka du -sh /tmp/kafka-logs` = **14 MB 真实数据**，而 compose 把 `kafka-data` 卷挂在 `/tmp/kraft-combined-logs`（**4 KB 空目录**）→ **持久化卷根本没生效，所有 topic 数据都在容器可写层**，任何 `recreate`/`down` 都会静默清空。这和之前 MySQL 丢数是**同一类问题重演**，但更隐蔽（auto-create 把"数据没了"伪装成"topic 正常"）。
- **方法学教训**：我第一版结论曾据"顶点指标 `write-records=0`"断言"job1 没读、全链路没重算"，而 TM 日志里 CDC 快照明明写着 `Finished exporting 182 records for split 'gmall_rt.payment_info:0'`。**先看日志确认事实，再用指标做监控——别用聚合指标代替日志。**
- **还带出一个验证方法学的坑**：`dws_trade_day` 是 upsert topic，旧值一直躺在 Kafka 里。如果链路没重算，job3 会把**上一次的旧值**原样转发进 MySQL → **锚点照样"全都对得上"**。**锚点一致 ≠ 这次算出来的**。所以核验重算要看**过程证据**（消费组位点 / source 读入量），更严的做法是先清空下游 topic 再重算（clean-room 验证）。

**第二幕：同一个终态、完全不同的成因（这层答出来档次立刻不同）**
哨兵后来报出 `ods_traffic_log` 的 `earliest=latest=**2000**` —— 注意**不是 0**。这就是分水岭：
`=0` 是"从没写过"（上面那个删除/重建竞态）；`=2000` 是"**写过、后来被删了**"（log start offset 前移、段文件没了）。
第一版哨兵把两者混为一谈，是**我自己工具的 bug**，已改成分开报。

真因在 broker 日志一句话：`Deleting segment ... due to log retention time 604800000ms breach based on the largest record timestamp in the segment` —— **Kafka 保留期**。关键语义是 **`message.timestamp.type=CreateTime` 时保留期按"消息自身时间戳"算，而记录时间戳 = producer 写入那一刻**（重放脚本的 `--ts 2026-09-01` 只写进消息体，**不是**记录时间戳）。所以这套"固定历史测试日"的数据集**写入满 7 天必被删**。
- 之所以一直没暴露：broker 停机跨过了 7 天界限，cleaner（5 分钟一轮）没机会跑；**容器一启动，33 秒后补删**（`Incremented log start offset to 2000`）。Kafka 会"先滚段再删"，**连活动段也删**。
- **差 79 分钟砍在演示上**：发现时 03:40 UTC，而 `dwd_traffic_event` 等 9 个 topic 的 7 天失效点是当天 **04:59 UTC**。且淘汰全程静默：topic 还在、13 个消费组 **lag 全 0**、14 作业 RUNNING、checkpoint 照常成功、**MySQL 里的指标还是旧值 → Grafana 看板数字看起来完全正确**。
- **修法分三层，且刻意绕开"必须重建容器"那条路**：topic 级 `retention.ms=-1`（10 个）+ broker 动态 `log.retention.ms=-1`（`log.retention.hours` 不能动态改）+ `start_env.sh` 每次启动幂等收敛。
- **最该讲的一个决策**：`KAFKA_LOG_RETENTION_HOURS: "-1"` 才是根治，但它会触发 Kafka 容器重建（`up -d --dry-run` 实测），而 `kafka-data` 卷正挂错路径 → 重建 = 清空全部 topic（**正是刚抢救回来的那批**）。所以我**故意把它注释在 compose 里并写明原因**——避免"顺手加一行配置"变成"下次启动清库"。**能识别出"正确配置"和"当前能安全执行的配置"不是一回事，比会改配置更值钱。**
- **一句话总结**：保留期是数据层的心跳——**它删你的数据，不报任何错**。
