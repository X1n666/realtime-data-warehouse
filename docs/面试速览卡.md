## 1. 一分钟主线（开场用）

> "我先用 Docker 搭了 MySQL/Kafka/Flink 环境，**用生成器造出可重现的三阶段交易数据**（这是能对账的前提）；然后**竖切一条最小链路**跑通 ODS→DWD→DWS→ADS；接着接入支付/退款/下单 CDC 建交易域，并**用批 SQL 做流批对账**，做到日口径 9 项指标分毫不差；再把作业**拆成物理四层**、上 Grafana；最后补分钟层时踩到一个**事件时间乱序导致水位跳变、窗口大面积不触发**的坑，用分层排查法定位并重放修复。全程记录在开发日志，已开源。"

**主线七个字**：搭环境 → 竖切跑通 → 接交易域 → 对账证明数对 → 分层工程化 → 深水区排障 → 闭环交付。

## 2. 七步主线 · 每步一个可讲的坑

| 步骤 | 做了什么 | **可讲的坑 / 亮点** |
| --- | --- | --- |
| ① 环境与数据底座 | Compose 起 MySQL(binlog ROW+FULL+30d)/Kafka/Flink/Grafana；9 张业务表；三阶段交易生成器 + 行为日志生成器 V2 | **数据可重现是能对账的前提**——同 seed 重放结果一致，批侧才算得出同一个数。随机造数的人对不了账 |
| ② 竖切最小链路 | ODS→DWD(去重)→DWS(1min 窗口 PV)→ADS(MySQL) | `ROW_NUMBER` 去重输出的是 **changelog**，append sink 编译报错 → 必须用 **upsert-kafka** 承载 |
| ③ 交易域接入 CDC | 支付 / 退款 / 订单明细 三条 CDC 支线 + 日聚合 | ① CDC 要显式 `server-time-zone=Asia/Shanghai`（否则 +8 vs Etc/UTC 时区校验失败）② **多作业必须分段 server-id**，否则互相踢下线 ③ **日聚合用 `GROUP BY CAST(ts AS DATE)` 而非窗口**——窗口要求事件时间单调，而 CDC 快照按主键扫描、天生乱序 |
| ④ 批流对账闭环 | 每指标用批 SQL 独立算一遍，流批逐值比对 | ① **红线：日 PV/UV 必须独立重算，禁止 `SUM(分钟)`**（分钟之和 ≠ 日值）② 主动解释"分钟 636 vs 日 641"是**尾部未触发窗口的预期差异**，不是 bug——**能区分"已知差异"和"未知 bug"是数据质量的核心能力** |
| ⑤ 分层 + 可视化 | 拆成物理四层 12 作业；Grafana provisioning 声明式注册 | **同一个 SQL 文件里的多个 INSERT = 多个独立作业**（Flink SQL 特性），但它们会共享 source 的 `group.id` → **partition 被一个作业独吞、另一个空转**。踩了两次，教训：**每新增一个 INSERT 分支，就必须再立一份 source DDL + 独立 group.id** |
| ⑥ 分钟层 + 深水区排障 | 补分钟 UV、交易分钟表；看板补分钟层 | **全项目最值钱的 bug**：CDC 快照按主键扫描输出 + 测试数据 id 与时间错位 → topic 内**事件时间乱序** → upsert-kafka 水位按物理消费序推进，**先读到晚事件后，其后所有早事件被判迟到丢弃** → 窗口只 fire 了 43 个就停。<br>**分层排查法**：非窗口日聚合对账正确 → 怀疑窗口 → 临时无窗口统计验证全量 ✓ → dump topic 时间序列看到乱序 → 定位到机制层。<br>**修复**：一次性按时间序**重放**成"真实事件流" |
| ⑦ 闭环 + 工程化 | 订单明细 CDC 补全生命周期；`start_env.sh` 一键启动；开源发布 | ① **作业风暴**：提交命令误执行两次 → 同 server-id 的 CDC 作业互踢 → 15 个作业 RESTARTING 循环，cancel 与 restart 赛跑清不掉 → 正确恢复 = **重启 jobmanager**（standalone 无 HA，作业全灭但 Kafka/MySQL 数据不丢）→ 按依赖序重提。教训：**恢复用"全灭重建"而不是逐个 job cancel** ② GitHub **100MB 限制对历史对象同样生效**——只 `git rm --cached` 不够，得重写历史 |

## 3. 深挖问答（面试官追问时用）

### Q1：你的 checkpoint 怎么配的？怎么证明容错生效？
- 配置：`execution.checkpointing.interval = 30s`、`state.checkpoints.num-retained = 3`。
- **配置了 ≠ 验证了**。诚实的答法是："配置是 X；恢复演练我做了/还没做（见第 4 节）"。
- **可延伸（本项目实测数据）**：`GET /jobs/<jid>/checkpoints` 拿到真实值——四类作业 checkpoint 耗时 **3–12 ms**、体积最大 ~0.6 MB；间隔 30s 时 `completed` 计数稳定增长、`failed=0`，这是"checkpoint 机制在正常工作"的直接证据。
- **checkpoint 间隔是吞吐与恢复时间的权衡**：间隔小恢复快但开销大；间隔大开销小但故障后重放的数据多。

### Q1b：你的 checkpoint 存在哪儿？（**答这题能看出是不是真跑过**）
很多人只答得出"间隔/超时"，答不出**存储位置**。本项目的运行时真值（`/jobs/<jid>/checkpoints/config`，不是文档抄的）：

```
state_backend      = HashMapStateBackend        ← 状态在 TM 堆
checkpoint_storage = JobManagerCheckpointStorage ← checkpoint 在 JM 堆
externalization    = false                       ← cancel 后不保留
state.checkpoints.dir = 未配置
```

**这是本项目的一个真实局限，主动讲反而是加分项**：

- checkpoint 元数据 + 状态字节**全在 JobManager 堆内存**，而 jobmanager 容器**没挂持久化卷** → **JM 一丢，所有 checkpoint 一起丢，无从 restore**；standalone 又无 HA，JM 重启后作业不会自动拉起。
- 所以我这边的恢复手段是**无状态全量重算 + 幂等覆盖写**，而不是从 checkpoint restore。**能说清"我的容错设计假设了哪一层不可靠"比背参数值有价值得多。**
- 再深一层（**这层很少有人知道**）：`JobManagerCheckpointStorage` 用 `MemCheckpointStreamFactory` 写状态，`checkSize()` 超过 `DEFAULT_MAX_STATE_SIZE = 5 MB` 会**直接抛 IOException 让 checkpoint 失败**（不是告警）。当前实际值 ~0.6 MB 很安全，但**去重状态一旦增长就会撞崖**——这条正好把 Q2 的 TTL 话题接起来。
- 修复方向：设 `state.checkpoints.dir: file:///opt/flink/checkpoints`（存储自动切 `FileSystemCheckpointStorage`）+ 两容器挂同一命名卷同路径。

### Q2：你的状态会不会无限增长？TTL 怎么设？
**这是本项目的加分题**，答错很常见：

- **开源 Flink 的 `table.exec.state.ttl` 默认值是 `0` = 永不过期**（官方描述原文："Default value is 0, which means that it will never clean up state."）。**阿里云 VVR ≥4.0.12 默认是 1.5 天**——**两边不一样，别答混**。
- 项目里**按"状态是否有界"分类处理**：
  - **job1 的 `event_id` 去重状态 = 无界**（∝ 累计去重键数）→ 必须显式设 `table.exec.state.ttl = 24h`；
  - **job2 的窗口状态**：窗口 fire 后自动清理 → 不需要 TTL；
  - **job2 的日聚合状态 = 有界**（∝ 日期 × 指标基数）→ **刻意不设 TTL**。
- **为什么不给日聚合设 TTL**（说得出这条很加分）：它的 `COUNT(DISTINCT uid)` 保留去重集合，若 TTL 过短，迟到数据到达时状态已被清理 → 聚合**从零重算，写出错的日指标**（可能报 `Can not retract a non-existent record`）。**TTL 不是越短越好——取值必须小于业务可接受的重算窗口。**

### Q3：你的链路是端到端"精确一次"吗？
**答"是"就露馅了。** 正确答法：
- Kafka 侧开 checkpoint 后 sink 走**两阶段提交**，链路内 exactly-once；
- 但 MySQL sink 用的是 JDBC **幂等写**（`ON DUPLICATE KEY UPDATE`）→ 整体是 **at-least-once 投递 + 幂等落库**；
- 因为最终形态是**按主键覆盖**，重复消费不产生重复指标——**用幂等性换取了不引入 2PC 的复杂度**。这也是我故障恢复时敢用"全量重算 + 覆盖写"的依据。

### Q4：多个 source 时水位怎么推进？某个源没数据会怎样？
- 作业水位 = **所有 source 水位的最小值**。某个 source 长时间无数据，它不推进 → **会拖住整个作业**，导致下游窗口不触发。标准解法是 `table.exec.source.idle-timeout`（默认 `0` = 关闭）。
- **但要讲清代价**：源被标记 idle 后水位可前冲，之后到达的（略晚的）数据会被判迟到丢弃。**该值要结合数据到达节奏定**，本项目流量是突发型生成，所以没有贸然开启。

### Q5：并行度怎么定的？
- 本项目**并行度 = 1、topic 分区数 = 1**，这是单机资源下的合理取舍。
- **但要能答出约束**：*"source 的并行度受**分区数**上限约束——1 个分区时并行度设 8 也只有 1 个 subtask 在消费。要提吞吐得先扩分区再提并行度，同时注意扩分区会改变 key 的分区规则。"*

### Q6：为什么 DWD/DWS 用 upsert-kafka，ADS 用 MySQL？
- DWD/DWS 是**变更流**（去重/聚合产生 update/delete 语义），append 模式表达不了 → upsert-kafka 按主键覆盖；
- ADS 是**面向查询的结果层**，需要 MySQL 提供低延迟点查给 Grafana → `ON DUPLICATE KEY UPDATE` 覆盖写。

## 4. 诚实清单（别吹过头）

**已做且已验证**：日口径 9 项指标流批逐值对账 ✓、分钟层 162×2 + 33×2 窗口 ✓、12 作业 RUNNING ✓、`start_env.sh` 幂等重跑 ✓、状态 TTL 已配置 ✓、**全量重算幂等性实测**（12 作业全灭后重提交，9 项指标与基线逐值一致）✓、checkpoint 机制在跑（`failed=0`，耗时 3–12 ms）✓。

**已配置但尚未验证**（面试若问，如实说"配置好了、演练还没做"，**不要含糊说成"验证过"**）：
- **checkpoint 故障恢复演练**（kill taskmanager → 观察自动恢复 + 状态不丢 + 指标不重复）——**这是最该补的一项**。
- **从 checkpoint/savepoint restore 的完整链路**：因为 checkpoint 存在 JM 堆里且无持久化卷，"恢复"这条路在当前配置下根本走不通；已验证的是**无状态全量重算**这条路。

**已知局限（被问到要承认，别绕）**：
- checkpoint 存储未落盘：`JobManagerCheckpointStorage` + jobmanager 无持久化卷 → **JM 丢失 = checkpoint 全丢 + 无法 restore**。修复方向见 Q1b。

**尚未做（如果面试官问"还能怎么优化"，主动说出来反而加分）**：
- **维度建模**：`user_info` / `base_province` / `base_category` / `spu_info` / `sku_info` 五张维表目前**未被消费**，只有事实表没有维度 → 下一步用 **Lookup Join** 产出分省 GMV / 品类 TopN（并讲**维表缓存 `lookup.cache.max-rows` + TTL** 的一致性与打库权衡）。
- **监控**：未接 Prometheus，缺 checkpoint 时长/反压/Kafka lag 的可观测性。
- **并行度与分区**：均为 1，未做吞吐对比实验。
- **Savepoint**：未做过 `stop --withSavepoint` 的版本升级演练。
