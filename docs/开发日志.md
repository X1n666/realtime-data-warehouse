## 节点 1：Job1 加 CDC 分支（payment_info → dwd_payment_detail）✅ 2026-08-24

### 做了什么
在 `flink-sql/job1_ods_to_dwd.sql` 追加三段：CDC source（payment_cdc）+ upsert-kafka sink（dwd_payment_detail）+ INSERT 透传。

### 为什么这么做（面试可讲的设计决策）
1. **source 声明 `PRIMARY KEY (id) NOT ENFORCED`**：mysql-cdc 输出 changelog（+I/-U/+U/-D），主键声明是下游按 key 合并 -U/+U 的前提。**不声明 = -U/+U 被当两条 append 记录 = 后续 GMV 聚合翻倍**。
2. **不做 ROW_NUMBER 去重**：id 唯一性由 MySQL PRIMARY KEY 保证（NOT ENFORCED 只是 Flink 不校验，上游已保证）。与流量域对照：Kafka 无主键 → 必须 event_id 去重。
3. **sink 主键选 id（支付流水）不选 order_id**：同订单可有多条支付流水，order_id 做主键会压丢流水、GMV 少算。
4. **sink 9 列 vs source 12 列**：丢 out_trade_no（与 trade_no 语义重叠）/ subject（冗余展示信息）/ update_time（CDC 位点由 Flink 管理）；保留 trade_no（渠道对账）、payment_type（维度）、callback_time（支付时长分析）。
5. **类型**：datetime → TIMESTAMP(0)（source，秒精度原生）→ sink TIMESTAMP(3) 需显式 CAST（Flink 不同精度不隐式转换）。

### 如何验证
- Flink UI：job1 变成 **2 个作业实例**（流量分支 + CDC 交易分支）均 RUNNING
- 消费 dwd_payment_detail topic：**182 条** = payment_info 182 行 ✓

### 出错重跑方法
```
# Kafka 数据丢（如 Docker 重启）：
docker compose up -d
# 重建 topic + 重灌日志（脚本见节点 1 命令历史）：
python data-generator/generate_action_log.py --seed 20260901 --count 2000 --active-users 500 --ts "2026-09-01 08:00:00" --output - | docker exec -i gmall_kafka /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic ods_traffic_log
# 重提交作业：
bash scripts/submit_sql.sh flink-sql/job1_ods_to_dwd.sql job1_ods_to_dwd
```
> 幂等性：dwd_payment_detail 是 upsert-kafka（key=id），重放覆盖写不重复；流量域 ROW_NUMBER 去重后重放无副作用。

## 修复：job2 双 INSERT 共享 consumer group 导致 DWS 层空转（Day4 遗留 bug）✅

### 现象与根因
job2_dwd_to_dws.sql 里 dws/ads 两个 INSERT 提交为**两个独立作业**，但都引用同一个 source 表（group.id=job2_dwd_group）。Kafka 1 partition 的消息只会被 group 内一个 consumer 消费 → 一个作业拿全量，另一个空转。**Day4 只验证了 ads（636 ✓）漏了 dws**；实测 dws_traffic_1m 为 0。

### 修复
给 ads INSERT 定义独立 source `dwd_traffic_event_ads`（同 topic，group.id=job2_ads_group）→ 两作业各自消费全量。

### 验证
- dws_traffic_1m：33 窗口 PV=636 ✓（修复前 0）
- ads_traffic_1m：33 窗口 PV=636 ✓（不受影响）

### 面试价值（问题 #7）
多个 Flink SQL 作业复用同一 DDL source = 共享 consumer group = 消息被瓜分。**教训：每个作业分支必须独立 group.id；验证必须覆盖每一条输出路径**（Day4 只查了 ads 漏了 dws）。

## 节点 2：交易 DWS 日聚合（GMV/支付订单数/支付用户数）→ ads_trade_day ✅ 2026-08-24

### 做了什么
1. 新建 `flink-sql/job2_trade_dws.sql`：消费 dwd_payment_detail → 3 指标按支付日聚合 → dws_trade_day（upsert-kafka）+ ads_trade_day（MySQL JDBC）
2. **环境改造（slot 8 + 持久化）**：6 作业 > 4 slots（NoResourceAvailable 无限重启）→ TM slots 4→8；mysql/kafka 数据挂 named volume（kafka 镜像 log.dirs=/tmp/kraft-combined-logs）+ 全部容器 restart: unless-stopped（Docker 两次退出丢数据教训）→ recreate 后导入 mysqldump 备份 + 重灌日志 + 重提交作业

### 为什么这么做
1. **GMV 聚合选"非窗口 GROUP BY CAST(create_time AS DATE)"而非 TUMBLE 窗口**：非窗口 = 持续累计（upsert 更新当日值），无 watermark/迟到/窗口触发问题，支付记录任何时刻到达都归入其支付日——对账简单可靠；窗口聚合要等窗口结束才输出，测试日一次性回放尾部数据会被卡住（流量域 5 条尾部数据的教训）。
2. **交易日指标表无 window_start**（对照实际 DDL：日表 PK=(metric_date, metric_name, dimension_key)；分钟表才有 window_start）。
3. **3 指标用 UNION ALL 合并成 2 个 INSERT**（dws 1 + ads 1），避免 6 个作业；每个 INSERT 独立聚合状态（SUM / COUNT DISTINCT 各自计算）。
4. **金额 SUM 输出 DECIMAL(18,2)**：SUM(decimal(16,2)) 精度 = decimal(38,2) → 输出统一 CAST DECIMAL(18,2) 兼容通用表结构。
5. **GMV 口径**：WHERE payment_status='SUCCESS' 不过滤其他状态（锚点 4：SUCCESS 金额不退 refund——退款的扣减在 refund_amount 指标单独表达，不加到 GMV）。

|---|---|---|---|
| gmv | 1,136,485.35 | 1,136,485.35 | ✓ |
| payment_order_count | 182 | 182 | ✓ |

## 节点 3：退款域（refund_detail CDC → refund_amount 指标）✅ 2026-09-03

### 做了什么
1. [job1_ods_to_dwd.sql](../flink-sql/job1_ods_to_dwd.sql) 追加第 3 分支：`refund_cdc` source（mysql-cdc 12 列全字段，server-id `5410-5414`，table-name=order_refund_info）+ `dwd_refund_detail` sink（upsert-kafka，7 列，PK id）+ 透传 INSERT（create_time CAST TIMESTAMP(3)）
2. 建 topic `dwd_refund_detail`（1 partition，与其他 topic 同规格）
3. [job2_trade_dws.sql](../flink-sql/job2_trade_dws.sql)：dws/ads 两个 INSERT 的 UNION ALL 各追加第 4 个 SELECT（`refund_amount` 指标，dws 版 FROM dwd_refund_detail、ads 版 FROM dwd_refund_detail_ads——独立 group.id 原则不破）
4. 重部署：cancel 旧版 job1×2 + job2_trade_dws×2 → 重提交新版。**cancel 后重提交 = 作业无状态全量重算 + upsert 覆盖写 = 幂等**（重算结果与旧值相同则覆盖写同值，下游数据不变）

### 为什么这么做（面试可讲）
1. **退款是独立指标体系，不是 GMV 的减项**：GMV 口径锚点 4 = SUCCESS 支付金额不退 refund；退款金额单独成指标（锚点 7），两表分算才能分别回答"卖了多少钱"与"退了多少"。
2. **退款源表与支付源表分开 CDC**：order_refund_info 有自己的流水 id/状态/时间，拆开才能按退款时间归日（退款可滞后支付 1-2 天，见下方验证——真实业务正是如此）。
3. **同一作业多 CDC source 必须独立 server-id 段**：refund 用 `5410-5414`，payment 用 `5400-5404`；同 MySQL broker 上相同 server-id 会被互相踢下线。
4. **sink 7 列丢 5 列**：refund_type/refund_num/refund_reason_*/update_time 属分析维度与 CDC 内部字段，明细层只保留聚合必需的 id/用户/订单/sku/金额/状态/时间。
5. **指标并入既有 INSERT 不加作业数**：4 指标 × 2 分支 = 2 作业；加第 5 个指标仍不加作业（UNION ALL 的每段独立聚合状态）。
